                                   Abstract
Exponential growth of image sharing on social media raises concerns about data
privacy. Traditional algorithms like AES are resource intensive. There is a need
for a Lightweight Cryptography algorithm (LWC). This paper presents a high
speed, quantum-resistant Salsa20 (256-bit) stream cipher for image encryption
using an NVIDIA GPU. Data parallelism using CUDA C reduces computa-
tion time for Salsa20. Simulation results on NVIDIA Tesla T4 and GeForce
RTX A4000 GPUs have massive speedup of 265x and 1381x over CPU execu-
tions, respectively. The configuration 8192 blocks and 8 threads is identified and
exhibits less computation time. The proposed accelerator has been validated by
conducting histogram analysis, memory usage, power efficiency and throughput.
This study reports a secure and time-efficient GPU-accelerated Salsa20 stream
cipher for real-time social media image encryption.

Keywords: CUDA, Parallel Processing, Image encryption, Salsa20, Lightweight
Cryptography.

1 Introduction
In the digital era, images are extensively used for medical diagnosis, social media, and
cloud data. With the growth of the internet world, image storage and transmission have
increased. There is concern about data privacy, security, and unwanted access. Image
encryption is a technique to hide image data in a scrambled form. The image contains
more data than the text file in a single form. That’s why traditional algorithms are
not suitable; it needs a different approach, like the LWC (Lightweight Cryptography)
algorithm. LWC algorithms are less resource-hungry and work faster than traditional
algorithms. One of the LWC stream ciphers is Salsa20. Salsa20 was designed by Daniel
J. Bernstein in 2005.
    Though the round functions of Salsa20 are suitable for parallel fine-grained accel-
erators (GPU). This paper focuses on enhancing the performance of image encryption
and decryption using quantum-resistant Salsa20 on GPU-based accelerators. The
Salsa20 algorithm is parallelized in different ways to reduce the computation time.
The 20-round Salsa20(256 bit) stream cipher is a very fast and efficient algorithm that
is recommended as a quantum-resistant algorithm Panda and Chattopadhyay (2019).

2 Fundamentals of Salsa20
Salsa20 is an LWC stream cipher. It explains using the figure 2 below.




Fig. 2 Salsa20 Block Diagram

    Depending on the particular variant being used, a key length of 16 bytes (128-bit)
or 32 bytes (256-bit) may be used in the Salsa20 algorithm. A nonce, a number that
is used only once, is used to guarantee the creation of a unique keystream; in Salsa20
the nonce size is 8 bytes. The algorithm also needs 8-byte block counter as an input.
Therefore, the key, nonce, and block counter are the necessary inputs of the Salsa20
encryption process.
    The algorithm is designed in two main parts, the expansion function, also known
as internal state matrix initialization, and the Salsa20 core function. The expansion
function performs state matrix assignment. Details of the expansion function are pro-
vided below in the paper. Salsa20 core function contains row round and column round
functions. Functions have 10 row rounds and 10 column rounds functions i.e total of
20 rounds. This function creates confusion and diffusion, same as hash function. Out-
put of a Salsa20 core function (64 bytes) and 64 bytes of input data are XORed to get
the ciphertext (64 bytes). The salsa20 has three parts:
1. Expansion function, i.e., internal state matrix
2. Round function
3. XOR function

2.1 Expansion function or internal state matrix
It is a 4x4 matrix of 32-bit (4 bytes) words. Total 16 elements, i.e., 16x4=64 bytes in
length. The state matrix has four main components.
1. Constant: It is also called ”Constant words”. It has 4 elements of 4 bytes each.
   Constant words are generally a string ”expand 32-byte k”.
2. Key: Key size is 128 bits or 256 bits.
3. Nonce: Nonce is a unique number used once per message.
4. Counter: It indicates the position number, which is 8 bytes. This can go to any
   point in the stream.

                                     c0 k 0 k 1 k 2
                                     k 3 c1 no n1
                                     b0 b1 c2 k 4
                                     k 5 k 6 k 7 c3
   In the above matrix, k is the key, n is the nonce, c is a constant, and b is the
counter. This matrix indicates the internal state matrix.

2.2 Quarter Round
Quarter round has 32-bit words as input. It follows three operations on 32 bits.
1. Add
2. Rotate
3. XOR




                                           7
   This is called the ARX operation. If a, b, c, and d are 4 input elements, then the
quarter function processes as b, c, d, a sequentially.

                                 b = b ⊕ ((a + d) ≪ 7)                                 (1)

                                 c = c ⊕ ((b + a) ≪ 9)                                 (2)

                                 d = d ⊕ ((c + b) ≪ 13)                                (3)

                              a = a ⊕ ((d + c) ≪ 18)                                   (4)
   Quarter function has 4 column rounds and 4 row rounds.

2.3 Number of rounds
The Salsa20/20 variant uses 20 mixing rounds whereas Salsa20/8 uses 8 mixing rounds;
other variants with fewer rounds are also defined. These mixing rounds are associated
with multiple applications of the round functions of the algorithm that increase data
mixing to a higher degree. The higher the number of rounds, the more extensive is the
interaction between data elements so that every word in the state will affect all the
others. In the Salsa20/20 design, the 20 mixing rounds are allocated in both column
and row operations. This process of diffusion is reinforced in this way, so that a single-
bit change in the key spreads over the entire state matrix and has a significant effect
on the output produced.

2.4 Generation of Keystream
After performing 20 rounds, the final step is to make the last results irreversible.
1. Add Initial State: The original internal state matrix is added word-for-word to the
   final mixed matrix. By doing this, the attacker prevented running around backward
   to get the initial state.
2. Output: The result is 64 bytes block of the keystream.
    To encrypt data of any arbitrary length, the block counter in the original internal
state matrix gets increased with every next block. This algorithm is repeated again
and again to produce the following 64-byte segments of the keystream which are then
used in succession to process the whole message.

2.5 Encryption/ Decryption
Salsa20 is symmetric in nature, which means for encryption and decryption, the same
process is followed.

                        Ciphertext = P laintext ⊕ Keystream                            (5)

                     P laintext = Ciphertext ⊕ Keystream                               (6)
By using XOR twice, the original state can be achieved.

6.2 Comparison with Existing Methods
The Salsa20-256 GPU accelerator’s algorithmic structure is favourable for massive
parallelism. It requires 0.31 rounds per byte, whereas AES-256-CTR requires 0.88
rounds per byte and ASCON-128a requires 1.50 rounds per byte, and these advantages
are magnified under GPU parallelization. The proposed method is more efficient than
the previous GPU-based implementation of Salsa20 Khalid et al. (2013), and the
execution time is minimized when the kernel is optimized with an 8192-block × 8-
thread configuration.




                                                  28
6.3 Threat Model, Compatibility with Image Compression
    and Metadata protection
Threat Model. This work assumes a threat model where the social media platform
is trusted (or honest-but-curious) for the confidentiality of the media content, but
no trust is placed in any network intermediary or any third party that accesses the
platform. This paper concerns only the encryption primitive, not key distribution. The
sender and intended recipient(s) are assumed to have previously shared a secret key
using a key exchange protocol that is beyond the scope of this paper (e.g., an out-
of-band protocol, or a key-management service in companion mode). The platform is
assumed to correctly pass through the ciphertext bytes it receives, although in practice
this is often untrue, as most platforms automatically recompress or resize uploaded
media - a threat to correctness addressed directly below. Explicitly out of scope are
attacks on key confidentiality, multi-party group key management, forward secrecy
across key rotations, and traffic-analysis or timing-based inference attacks.
    Compatibility with Image Compression. The encrypted data is statistically
similar to white noise ( entropy = 7.99-8.0 bits, chi-square uniformity testing), and is,
therefore, unsuitable for any lossy compression schemes, like JPEG, or lossy WebP,
which require a certain amount of spatial and statistical redundancy that encryption
is the key to removing. We empirically established this in our robustness testing :
re-compression at JPEG quality 75 of an encrypted image results in significant and
unrecoverable pixel corruption. The practical impact of this is for deployment: most
social media platforms will automatically recompress images uploaded through a typi-
cal photo upload endpoint and this would silently corrupt any payload with pixel-level
encryption. It will be necessary either to upload encrypted images that are Bytes
Lossless (e.g., not via photo-specific upload API but as a generic file/document attach-
ment, or via lossless formats like PNG if supported), or to have a dedicated client
application or browser extension that intercepts and re-encrypts media via a channel
the platform does not recompress. Any resizing the platform does is equally lethal as it
would destroy the mapping of pixels to keystream that the cipher relies on; encrypted
images would have to be sent at a fixed resolution anyway, one which the platform is
supposed to preserve.
    Metadata protection. The proposed scheme only encrypts the image informa-
tion (the content of the pixels) and not the image metadata. Even though the actual
image content is protected, the dimensions and number of the image channels are visi-
ble in the (unencrypted) file container header, and are necessary to correctly assemble
the pixel buffer for decryption. Similarly, EXIF (camera model, GPS data, etc.) at the
pixel level would require stripping or hiding and re-encrypting if it was to be uploaded,
a task we do not perform in this work. Metadata of account identity, file upload time,
and file size are not hidden from the platform or any network observer and are a close
approximation to raw resolution × channel count for near-random ciphertext. This
metadata is orthogonal and requires EXIF stripping, dimension padding/standard-
ization to reduce resolution fingerprinting, and encrypted or out-of-band metadata
channels, which we see as needed supplements to this work but are not the subject of
this document.

6.4 Limitations and Deployment Considerations
Limitations. The generated ciphertext is not authenticated; production use would
require an authenticated mode to prevent undetected tampering or bit-flipping attacks.
Robustness testing reveals that lossy recompression (e.g., JPEG) destroys the cipher-
text, since encrypted images approximate random noise and are designed to be
incompressible. This limits deployability to platforms or pipelines that ensure lossless
transport of encrypted content.
    Deployment Considerations. Based on this, there are a number of challenges
for the practical deployment of the proposed scheme: (1) a client-side application or
browser extension to encrypt before upload, with an upload path that avoids platform
side recompression or dimension resizing; (2) need for an extra secure key-management
and key distribution layer, as key exchange is not part of this work; (3) need for EXIF
stripping and dimension aware handling before encrypting to reduce the amount of
metadata that can be leaked; and (4) need for an authenticated encryption mode
or integrity tag verification because this scheme only provides confidentiality, and
not integrity, before the upload. The throughput and low latency capabilities of the
scheme described in Section 5 make it suitable for use in various applications such
as client-side pre-upload encryption on a GPU or NPU, ephemeral-media features in
messaging applications, and bulk server-side encryption pipelines for platforms that
wish to preserve lossless transport for encrypted content.

7 Conclusion
There are two hardware configurations. The former system comes with an Intel Xeon
CPU operating at 2.00 GHz and an NVIDIA Tesla T4 graphics card having 16 GB
memory. The second is an Intel Core i9-14900K CPU with a speed of 3.20 GHz and
an NVIDIA GeForce RTX A4000 graphics card, and 16 GB of RAM, as well. The
suggested parallel implementation has been shown to be quite accelerated with a 265x
and 1381x speedup(without PCIe data transfer overload) of the parallel implementa-
tion compared to the serial version on the first and second systems, respectively, and
shows performance enhancement.
    The histogram of the ciphertext image has a more balanced distribution of intensity
level, which means that it is less vulnerable to the statistical attacks. This consis-
tency implies that the encryption technique is effectively spreading pixel values hence
enhancing the robustness of security.
    In parallel CUDA C implementation, a difference in the time of encryption and
decryption are noted, despite the overall number of computational threads being the
same. Such differences may occur due to optimized Streaming Multiprocessor (SM),
effective hiding of memory latency, and efficient resource management. The perfor-
mance of the GPUs does not always increase in a linear fashion; rather, an ideal setup
is determined. In particular, the most time-efficient setup of 8192 number of blocks
and 8 threads per block is the fastest of the tested configurations, which is observed
on both hardware configuration.
    The above simulation is done for the data parallelism. The future scope of
research involves functional parallelism for the quarter-round function and verifying


                                          30
the results with proper image validation. With this simulation, it is expected to reduce
computation time.
    This paper shows a quantum-resistant Salsa20 (256-bit) image encryption algo-
rithm for parallel systems. The suggested solution works in speeding up image
encryption in resource-limited systems like handheld devices. Nowadays, social net-
works, such as WhatsApp, use the AES algorithm to encrypt images, which is
potentially even more time-consuming. In this respect, Salsa20 is an attractive alter-
native as it is efficient and has less computational overhead. As the level of GPU
functionality is becoming more widely available in modern handheld devices, the pos-
sibility to further minimize the encryption time is high, and thus, this method can be
very relevant to social media applications that require real-time image encryption. The
limitation of this work is that the programmer has to adjust total number of threads
according to size of the image to get the correct encryption and decryption.
